安全裕度与路径平滑

本文介绍空域载具八叉树三维寻路项目中的后处理环节：给上一节 A* 规划出的路径 加上安全裕度，并把它平滑成控制器可以跟踪的光滑曲线。

对应总纲第 5 节「安全裕度与路径平滑」。

2. 为什么需要这一节

A* 输出的路径是八叉树叶节点中心的序列，直接拿它去飞有两个问题：

问题 具体表现
没有安全裕度 路径航点落在自由叶的中心上，代价是"两节点中心的距离"，所以路径可以贴近障碍物。它只是没有撞上，没有留余量
是折线，且航点疏密不均 空旷处一步跨过十几米，障碍附近一步 0.3 m。折线拐角处的曲率为无穷大，控制器无法跟踪；同时有大量共线的冗余航点

本节做两件事来对应这两个问题：安全裕度（膨胀 + 代价惩罚）与路径平滑（捷径化 + 三次样条）。

3. 关键认识：两种安全裕度不是平级的

一个容易想当然的做法是把"地图膨胀"和"代价惩罚"当作两个并列的手段，任选其一。 实际它们是"硬约束"与"软偏好"的关系，本节的设计都建立在这个区分上。

回到 A* 的代价函数：

路径航点是自由叶的中心，于是：

只做代价惩罚 只做地图膨胀
不产生硬保证。惩罚只让贴近障碍的边变贵，A* 在别无选择时仍会贴过去——惩罚大只是"不划算"，不是"不允许" 让膨胀占用成为不可通行，路径中心到真障碍的距离有了下界 。这是硬保证

结论：

惩罚要消费膨胀算出的间隙，两者共用同一份信息，而不是各算一套距离。实现上对应 MapInflation（产出）+ clearance penalty（消费）两个组件，而不是两个平级开关。

4. 安全裕度（一）：地图膨胀 —— 硬约束

4.1 影子树

把原树里每个占用叶节点沿轴向外扩 ，把外扩盒内的体素全部标进一棵 影子树：

for 每个占用叶（中心 c、半边长 h）:
    盒子 = [c − h − r, c + h + r]
    把盒内的体素逐个标进影子树

于是"是否可通行"多了一道硬判定：

bool isBlocked(const point3d& p);   // true = 落在安全裕度内，不可通行

为什么用影子树而不是直接改原树：

  • 原树仍用于发 /octomap_full 和 RViz 可视化，前后占用体素一致
  • 膨胀的信息是新增的，不改建图结果
  • 时影子树为空、isBlocked() 恒为 false，整套代码退回上一节的行为 （这是回归测试的锚点，见 §7）

4.2 膨胀必须"按键枚举"，不能自己算坐标

这里有一处容易出错的地方。octomap 的体素中心落在

这组格点上。如果按"盒下界 + 半个体素"生成中心：

// 错误做法：与键格错开半个体素
const point3d q(lo.x() + (i + 0.5) * res, ...);

得到的格点与键格错开半个体素，"写入影子树的体素"与"判定时命中的体素" 不是同一批。症状是被膨胀的体素中心自己判不出阻塞（实测间隙 0.45 m，期望 0.6 m）。

正确做法是按整数键枚举：

OcTreeKey lo_key, hi_key;
tree.coordToKeyChecked(lo, lo_key);      // 先把盒的坐标范围落到键上
tree.coordToKeyChecked(hi, hi_key);
for (long long i = lo_key[0]; i <= hi_key[0]; ++i)      // 按整数键枚举
  for (long long j = lo_key[1]; j <= hi_key[1]; ++j)
    for (long long k = lo_key[2]; k <= hi_key[2]; ++k)
      tree.updateNode(OcTreeKey(i, j, k), true);        // 插入与判定走同一条路径

这样"插入的位置"与"判定时命中的位置"逐格一致。

4.3 取多大：安全性与可通过性的取舍

膨胀会不可逆地损失可通过空间：原来能走的窄缝，膨胀后可能消失。 所以 的选择是一个取舍：

效果
关闭膨胀，退回上一节行为（回归基线）
推荐值（2 个体素）：路径中心到真障碍至少留 0.6 m
更保守，窄通道可能被堵死，表现为"基线有解、加膨胀后无解"

"加膨胀后无解"是预期行为，不是缺陷，它是安全裕度的代价。 实测的膨胀规模见 §7。

间隙 的算法是近似：从节点中心沿 6 个轴向按步长探测，数到第一次 命中膨胀占用为止，并按 max_range 截断。它代价低，对软偏好足够， 但不是精确的欧氏距离（真实最近点可能在对角方向）。

6. 路径平滑

两步，顺序不能反。

6.1 第一步：捷径化（shortcut）

贪心地把折线取直：

for i in 0..n-1:
    for j from n-1 down to i+2:        # 从最远的候选试起，取直收益最大
        if 线段 p[i]→p[j] 无碰撞:
            保留 p[j]，丢掉 p[i+1..j-1]; break

三个要点：

  1. 碰撞检测用的是规划器自己的可通行谓词，它包含两层判定： 先查原树的占用与未知（未知一律当障碍），再叠加膨胀阻塞。 所以平滑也受安全裕度约束，不会把路径拉回障碍旁；规划与平滑共用同一套安全语义。 这两层都必须有 —— 少了原树那一层，inflation_radius = 0 时谓词会退化成 "任何位置都可行"，捷径化就会把路径直接取直、穿过障碍（§7 有用例覆盖）。
  2. 采样步长必须小于分辨率（默认 ）。 否则线段会从两个占用体素的对角缝里穿过去。这是安全关键项， 不是可以调大的性能参数（§7 有一条反例断言证明这一点）。 因此 smoothPath 强制 ： 显式传入的值只要 ≥ 分辨率，就被限幅到 ， 并在 SmoothStats 里标记、由节点打 WARN —— 不静默改参数，也不放行。
  3. 首尾两点保留：它们是任务给定的起点与终点。

6.2 第二步：三次样条

在捷径化后的折线上做自然三次样条插值（曲线过航点）：

  • 按累积弦长参数化
  • 对三个坐标分量分别解一次三对角方程组（Thomas 算法），自然边界条件
  • 逐段采样输出

不需要引入 Eigen 或第三方样条库。

6.3 拟合与逼近的取舍

路线 做法 优点 缺点
拟合 曲线过航点 贴合原折线 在拐角内侧向外偏离，可能侵入障碍
逼近 航点当控制点 曲线在控制点凸包内，更平滑 不过航点，会切角

本实现选拟合 + 复检 + 不过就退回折线。第一优先级是不引入碰撞， 平滑度在其次。平滑是增强，不能变成引入碰撞。

复检：样条按 重采样，逐点且逐段检查；只要有一点越界， 就整条丢掉、退回捷径化折线，并在日志里说明"被复检拒绝"。

7.4 进一步工作

本节实测暴露的两点，按性价比排序：

# 项 说明
1 拐角处保留航点再拟合 让样条不要在拐角被迫大幅弯曲，从而通过复检。这是让"拟合"路线真正可用的关键
2 改用逼近（B 样条） 航点当控制点，曲线落在控制点凸包内，不穿过拐角 —— 从根上避免"拐角外偏"（见 §6.3）
3 最小捕捉的平滑 把平滑写成一个带约束的优化（目标是最小化曲率或加加速度，约束是全程离障碍 ≥ 安全半径），比"先折线再拟合"更彻底。代价是需要引入二次规划求解器
4 指标的精确化 目前的最小间隙沿 6 个轴向步进探测（偏乐观）。精确做法是对每个路径点做 26 邻域欧氏距离变换，代价高得多

9. 实现中踩到的坑（供参考）

9.1 判定"是否被占用"不能用"子节点槽位是否为空"

这个判据造成过两个看起来无关的现象。

octomap 在合并/剪枝时会把连片的空闲兄弟删掉，把占用状态留在父节点上。 所以下面这种自己写的下潜判据是错的：

if (!nodeHasChildren(n)) return false;        // 错：当作"到底了，未被标占用"
if (!nodeChildExists(n, idx)) return false;   // 错：当作"该分支未分配"

它不能推出"该处未被标占用"。症状有两种：

  • 膨胀层：被膨胀的体素中心自己判不出阻塞，测出的间隙偏小
  • 上一节的常驻自检：findLeaf self-check: 2000 个自由叶里 172 个查不回来

解法：在影子树里直接用 octomap 自己的 search()。 影子树是逐个底层键插进去的，没有粗自由节点， 所以不存在"search() 遇到剪枝节点返回 NULL"的问题。

这不能照搬到主地图：上一节绕开 search() 的理由是成立的—— 剪枝后的粗空闲节点会让 search() 返回 NULL，而 A* 的路径要走这些大节点。 主地图的叶子查找需要两者结合。

9.2 八叉树遍历器的 key 与"叶子所在层的 key"不是同一个东西

selfCheckLookup 长期误报 172/2000，一度被当成"叶子查找有 bug"。 实际是自检的比较基准错了：它把遍历器报告的原生 key 直接和 "折算到叶子所在层的 key"相比，而遍历器的原生 key 把"该叶在父节点中的位置"留在低位。

实测的对应关系（树深 16）：

叶子深度 遍历器原生 key 折算后 右移位数
13 32772 4096 3 = 16 − 13
15 32777 16388 1 = 16 − 15

修法：比较前把遍历器 key 也右移 (树深 − 叶子深度) 位。 改完后，两种测试地图共 1519 个自由叶全部命中（KEY-DIFF = 0）。

结论：自检报"大量失配、但功能看起来正常"时，要先怀疑自检本身。

9.3 手写 octomap 的编译命令必须同时链两个库

liboctomath 是独立的库。只写 -loctomap 会报：

undefined reference to `octomath::Pose6D::transform(octomath::Vector3 const&)'
/opt/ros/noetic/lib/liboctomath.so.1.9: error adding symbols: DSO missing from command line

catkin 的 OCTOMAP_LIBRARIES 里两个都带，所以工程内不会暴露， 只有脱离 catkin 手写 g++ 时才会踩到。正确写法：

g++ -std=c++11 -I/opt/ros/noetic/include foo.cpp \
    -L/opt/ros/noetic/lib -loctomap -loctomath -o foo
