1. 无人机键盘控制（遥控链路）

把终端按键转换成机体系速度指令，经 carlair_ros_bridge 执行；验证 ROS 指令通道与仿真器联动。

任务①「无人机仿真 + 键盘控制」的 ROS 侧实现：把终端按键转换为机体系速度指令， 发布到 /uav/cmd_vel，由 carlair_ros_bridge 连仿真器执行。仿真/坐标换算/安全限幅 集中在桥接层，键盘、规划器、神经网络控制器共用同一条指令通道。

运行架构

终端按键 ──► uav_keyboard_control ──/uav/cmd_vel──► carlair_ros_bridge ──► CarlaAir/AirSim
            (raw 模式读键)        (geometry_msgs/Twist)   (坐标换算+执行)     (无人机)

按键映射

机体系（x 前 / y 左 / z 上）：

按键 动作 Twist 分量
W / S 前进 / 后退 linear.x = ±horiz_speed
A / D 左移 / 右移 linear.y = ±horiz_speed
R / F 上升 / 下降 linear.z = ±vert_speed
Q / E 右转 / 左转 angular.z = ±yaw_rate
松开 悬停 全零
ESC 退出 —

Q/E 的方向遵循 AirSim 机体系 yaw_rate 约定（Q=+yaw_rate 机头右转）。

实现要点

终端 raw 模式

Linux 终端默认行缓冲（要按回车），用 termios+tty 进入 raw 模式即可单键即时响应：

with RawKeyReader() as reader:        # __enter__ 切 raw，__exit__ 恢复
    key = reader.get_key(timeout=0.03)  # select 非阻塞读一个字符

with 语句保证 Ctrl-C 或异常退出时也能恢复终端设置，不会把用户的终端卡在 raw 模式。

按键 → 速度：纯函数

key_to_cmd(key, horiz, vert, yaw) 把按键映射为 (vx, vy, vz, wz)， step_once 再打包成 geometry_msgs/Twist。两者都不依赖 ROS/终端， 可在无 ROS 的机器上单元测试（tests/test_keyboard_local.py，35 项）。

松开即悬停

节点主循环 30 Hz，每轮循环发布一条 Twist：读到按键就发该方向速度，没读到（松开/未知键）就发全零；按键不锁存，要连续运动必须持续按键（自动化时即"定频重复注入"，见 7.6）。桥接层的 cmd_vel_sub 有「超过 cmd_timeout 无指令自动悬停」的安全保护，这里再叠加一层 显式零速度，双保险防止无人机失控。

与视口内置 WASD 的关系

CarlaAir 视口内置键盘操控（任务①的「仿真」部分），本模块提供 ROS 侧键盘控制 （任务①的「键盘控制」部分）。两者可对比验证：视口 WASD 直接驱动仿真器， 本模块走 键盘 → /uav/cmd_vel → 桥接 → 仿真器 的完整 ROS 链路，正是后续 规划器、神经网络控制器的通用入口。

按键闭环的复现方法

先看清语义：一个字节只产生一条速度指令

src/air/uav_keyboard_control/uav_keyboard_control/keyboard_node.py 的主循环：

def spin(self):
    with RawKeyReader() as reader:
        while not rospy.is_shutdown():
            key = reader.get_key(timeout=0.03)      # 没按键时返回 None
            if key == "\x1b":                       # ESC 退出
                break
            self.pub.publish(self.step_once(key))   # 每轮循环发布一条 Twist
            self.rate.sleep()                       # 30 Hz
  • 每一轮循环发布一条 Twist：读到键就发该方向速度，没读到键（None）就发全零；
  • 因此写入一个字节 = 一条非零指令，约 33 ms 后的下一轮循环就回落到零速。 按键不是锁存的：写一次 W 并不会让飞机持续前进，只会"推一下"。

这一点由评审在另一台机器上实测确认（Ubuntu 20.04 / ROS Noetic / 本机 Blocks+AirSim）：

注入方式 收到的非零 /uav/cmd_vel 水平位移
单次写入 W 1 条 约 0.20 m
以 20 Hz 重复写入 W、持续 3 s（60 次） 60 条 约 4.56 m

本页早期版本写的是「每个按键写一次字节、保持 2.5~3 s，节点在这段时间内持续发布该方向速度」—— 这是错的（作者当时误以为按键会被锁存），已删除；早期按该协议得到的位移数字 也不再作为定量指标。

两种可复现协议
协议 注入方式 注入频率 测量时段 预期观测
A 单次脉冲 只写一个 b"w" 一次 写入后 1.0 s 内的位姿差 1 条非零指令；位移约 0.20 m
B 定频注入 循环写 b"w" 20 Hz 连续 3.0 s（共写入 60 次） 60 条非零指令；位移约 4.56 m

测量方法（两条协议通用）：

  1. 客户机先按 7.2 启动桥接层与键盘节点，确认无人机已在目标高度悬停；
  2. 测量时段首尾各取一次位姿： rostopic echo -n1 /uav/odom/pose/pose/position，两者相减即水平位移；
  3. 同时统计指令条数核对"写入次数 → 非零指令条数"： rostopic echo -p /uav/cmd_vel/linear/x，数其中 != 0 的样本条数。

注意：桥接层 cmd_timeout 有"超时自动悬停"保护，定频注入的间隔要明显小于它 （默认 0.5 s），20 Hz（50 ms）远小于该阈值。

#!/usr/bin/env python3
# -*- coding: utf-8 -*-
"""用伪终端(pty)把按键按固定频率"敲"进 uav_keyboard_control，模拟真人连续按键。

为什么要定频重复写入：节点主循环每轮只发布一条 Twist（见文档 7.6.1），
写一次字节只"推一下"；要让飞机持续运动，必须按固定频率重复写。

用法：
  python3 kb_inject_test.py --mode pulse                         # 协议 A：单次脉冲
  python3 kb_inject_test.py --mode repeat --hz 20 --seconds 3    # 协议 B：20 Hz 定频
"""
from __future__ import print_function

import argparse
import os
import pty
import select
import sys
import time

CMD = ["ros2", "run", "uav_keyboard_control", "keyboard"]


def main():
    ap = argparse.ArgumentParser()
    ap.add_argument("--mode", choices=("pulse", "repeat"), default="repeat")
    ap.add_argument("--key", default="w")
    ap.add_argument("--hz", type=float, default=20.0)
    ap.add_argument("--seconds", type=float, default=3.0)
    ap.add_argument("--boot-wait", type=float, default=6.0, help="节点初始化等待 (s)")
    args = ap.parse_args()

    pid, fd = pty.fork()
    if pid == 0:                                  # 子进程：节点本体
        try:
            os.execvp(CMD[0], CMD)
        except Exception as exc:                  # noqa: BLE001
            sys.stderr.write("exec failed: %s\n" % exc)
        os._exit(1)

    print("[test] 节点已在伪终端中启动 (pid=%d)" % pid)
    time.sleep(args.boot_wait)                    # 等节点初始化并打印启动信息

    chunks = []

    def drain(seconds):
        """在 seconds 秒内持续把子进程输出读走（保持伪终端不被写满）。"""
        end = time.time() + seconds
        while time.time() < end:
            r, _, _ = select.select([fd], [], [], 0.02)
            if not r:
                continue
            try:
                data = os.read(fd, 4096)
            except OSError:
                return False
            if not data:
                return False
            chunks.append(data)
        return True

    drain(1.0)
    key = args.key.encode("ascii")

    if args.mode == "pulse":
        print("[test] 协议 A：单次写入 %r，测量时段 1.0 s" % args.key)
        os.write(fd, key)
        drain(1.0)
    else:
        period = 1.0 / args.hz
        count = int(round(args.seconds * args.hz))
        print("[test] 协议 B：%r 以 %.1f Hz 重复写入 %d 次，测量时段 %.1f s"
              % (args.key, args.hz, count, args.seconds))
        t0 = time.time()
        for i in range(count):
            os.write(fd, key)
            nxt = t0 + (i + 1) * period
            drain(max(nxt - time.time(), 0.0))
        print("[test] 定频注入结束，实际用时 %.2f s" % (time.time() - t0))

    # 松开：不再写字节，节点下一轮循环自动发全零
    drain(1.0)
    try:
        os.write(fd, b"\x1b")
    except OSError:
        pass
    drain(0.5)
    try:
        os.close(fd)
    except OSError:
        pass

    print("----- 键盘节点输出 -----")
    sys.stdout.write(b"".join(chunks).decode("utf-8", "replace"))
    print("----- 输出结束 -----")


if __name__ == "__main__":
    main()

为什么用世界系而不是机体系？ 实测 CarlaAir 里 SimpleFlight 的偏航保持不生效： 即使命令 yaw_rate = 0，机头仍以约 9°/s 漂移并 ±25° 摆动。若用机体系速度控制， 前进方向会随漂移的机头一起转，轨迹变成绕圈（实测半径 ≈ |v|/ω ≈ 0.8 m）。 改用世界系后，机头怎么转都不影响轨迹，策略才稳定收敛。

r   = sqrt(x² + y²)
θ   = atan2(y, x)                    # -π..π，0 = 正东
i   = ⌊(θ + Δ/2) / Δ⌋ mod 16        # Δ = 2π/16
h[i] = min over sector i of clip(r / R_max, 0, 1)      # R_max = 12 m

动作（4 维，[-1,1]）

vx = a[0] · 3.0        # 世界系东向速度 (m/s)
vy = a[1] · 3.0        # 世界系北向速度 (m/s)
vz = a[2] · 1.5        # 世界系天向速度 (m/s)
ω  = a[3] · 1.0        # 偏航角速度 (rad/s，不影响轨迹)

映射到 geometry_msgs/Twist 的 linear.x/y/z 与 angular.z。 因为是世界系速度，桥接必须以 body_frame:=false 启动（否则会被当成机体系）：

roslaunch carlair_ros_bridge main.launch publish_image:=false body_frame:=false

节点启动时会自动校验桥接的 control/body_frame 参数：读到 true 会打印 logerr 明确报错，读不到会 logwarn 提示，避免出现"无人机会飞但方向不对、 日志里却什么都没有"的隐蔽故障。

桥接的 control/cmd_duration（单条速度指令持续时长）默认 0.1 s，与本模块训练 环境的 dt = 0.1 s 对齐；若设成 0.2 s，指令作用时间翻倍，会造成过冲震荡。

训练

训练环境 scripts/env.py 是质点 + 速度环一阶滞后模型：

vel += (cmd_vel − vel) · dt / τ          # τ = 0.45 s，模拟真实速度环滞后
pos += vel · dt

随机摆放圆柱障碍物与随机目标，用射线-圆求交生成合成激光雷达直方图。 奖励 = 「向目标靠近的进度 − 动作平滑 − 时间惩罚」，到达 +20、撞障碍/越界 −20。

为什么要建模速度滞后？ 真实飞行器的速度环不是瞬时到达指令速度。早期版本 用瞬时质点模型训练，策略在 CarlaAir 里会因惯量过冲而来回震荡；加入一阶滞后后 明显改善。

安全速度包络（近障减速 / 急停）

策略是在质点环境里训练的，部署到仿真或真机时再加一层与策略解耦的兜底：直接复用 22 维观测里的 16 扇直方图，沿速度方向取净空（含相邻扇），据此限速。

条件 行为
点云缺失 / 空点云 / 超过 cloud_timeout 未更新 零速度（fail-safe，不假设“无遮挡”）
clearance > slow_distance 速度不变
stop_distance < clearance ≤ slow_distance 水平速度按 (clearance − stop) / (slow − stop) 线性衰减
clearance ≤ stop_distance 水平速度清零（急停），垂直速度保留以便脱离
水平速度 ≈ 0（悬停） 不判定方向，也不急停
  • 净空 = 扇形归一化值 × 12 m；速度方向按世界系 atan2(vy, vx) 分扇（0 = 正东，逆时针），与观测直方图完全一致；
  • 只缩放水平速度，垂直速度只做 ±1.5 m/s 限幅；
  • 参数：safety/enabled（默认 true）、safety/stop_distance（0.8 m）、safety/slow_distance（3.0 m）、safety/cloud_timeout（0.5 s），launch 里可用 safety_stop_distance:= / safety_cloud_timeout:= 等覆盖；
  • 传感器有效性优先于净空：节点按点云接收时刻算 age，缺失（no_lidar）、缺时间戳（no_timestamp）、过期（stale_lidar）时发布全零速度并 1 Hz 告警。这样“降级运行”不会退化成“蒙眼全速”；
  • 触发急停时按 1 Hz 打印 logwarn（含净空），便于区分“策略不敢走”和“包络把速度拦掉了”。

工程经验（sim-to-real 差距）

联调过程中定位到三个真实的落差来源，均已修正：

  1. 偏航不可控 → 改用世界系控制。CarlaAir 的偏航保持不生效（漂移+摆动）， 机体系控制会导致绕圈飞行。
  2. 速度环滞后 → 训练环境建模一阶滞后。否则策略在真机上因惯量过冲震荡。
  3. 控制周期必须一致。训练 dt = 0.1 s，部署也须用 0.1 s（用 0.25 s 会震荡）。

另外，CarlaAir 的仿真器在高密度几何 + 大点云场景下（楼群中激光雷达 9000+ 点） 单步 RPC 可达数秒，属平台性能上限，与策略无关。

3. 强化学习算法与网络结构对比

在同一环境与接口下比较 PPO / SAC / TD3，以及 MLP 加宽、加深与基准结构的差异。

在完全相同的环境与接口下，回答两个问题：

  1. 同模型不同 RL 算法：PPO / SAC / TD3 哪个学得快、学得好、飞得稳？
  2. 同算法不同网络结构：MLP 加宽（[256,256]）与加深（[64,64,64]）比基准（[64,64]）值不值？

环境直接复用 uav_ppo_nav 的 NavEnv（不复制、不改动）， 所以比出来的差异只反映算法或结构的差别。

实验设计

对比矩阵

维度 取值 说明
算法 ppo / sac / td3 同一结构 [64,64]、同一步数预算
结构 [64,64] / [256,256] / [64,64,64] 同一算法（PPO）
种子 0 / 1 / 2 每个配置重复 3 次，报告取均值 ± 标准差
预算 100 000 步 / 配置 三种算法一致 —— 对比的是样本效率，不是"谁训得久"
环境 场地 ±10 m、16 个障碍、目标 2~8 m 与 uav_ppo_nav 部署时的密度一致

公平性约定

  • 同一学习率 3e-4、同一折扣 0.99、同一批大小 256；
  • 同一网络结构：SB3 的 SAC/TD3 默认是 [256,256]，若不统一，差异里会混进 「网络更大」这个与算法无关的因素；
  • 同一批评估任务：固定 seed 的 100 个回合，全部用确定性动作（取策略均值，不采样）；
  • 其余保持 SB3 默认（SAC 自动熵调节、TD3 目标策略平滑等）—— 这些正是各算法的特征。

为什么不能只看成功率

只比成功率会漏掉两类实际不可用的策略：能到但绕远路、能到但抖得厉害。因此记录：

指标 含义
success_rate / crash_rate / timeout_rate 到达 / 碰撞或越界 / 超时（三者之和 = 1）
mean_steps 回合平均步数
path_efficiency 直线距离 / 实际飞行路程（0~1，越接近 1 越直；原地不动记 0）
action_smoothness 相邻两步动作的 L2 距离均值（越小越平滑）
train_fps / train_time_s 训练吞吐与墙钟时间（不同算法的训练成本差异极大）

path_efficiency 的"原地不动记 0"是本地测试抓出来的：最初实现用 min(1.0, 直线/路程)，悬停时路程为 0 导致除零后被截成满分 1.00 —— 不动的无人机反而拿到最优路径效率。已修正并有测试锁定。

结论与讨论

算法层面（结构统一为 [64,64]）

  1. PPO 在样本效率上明显领先：同样 10 万步，成功率 33% vs SAC 23% vs TD3 7%。
  2. PPO 的「飞行质量」优势比成功率更大：路径效率 0.81 vs 0.39 / 0.35 （接近直线 vs 绕来绕去），动作平滑度 0.117 vs 0.517 / 0.696（抖动是 PPO 的 4~6 倍）。 这正是只看成功率会漏掉的部分 —— SAC/TD3 能到达目标，但飞得又绕又抖。
  3. 「碰撞率低」是个陷阱：SAC/TD3 的碰撞率（6%）反而低于 PPO（22%），但超时率高达 70% / 86%。碰撞少不等于更安全，而是「不敢动」 —— 这类结论必须结合超时率一起读。
  4. 训练成本差 8.5 倍：PPO 平均 1039 步/秒，SAC 仅 122 步/秒（off-policy 每步都要做 梯度更新）。同样墙钟时间里 PPO 能多跑近一个数量级的样本。

显著性说明（重要）：从学习曲线看，PPO 与 SAC 的误差带大面积重叠 （PPO 33%±7% vs SAC 23%±10%，训练到 6 万步时 SAC 甚至反超）。 因此「PPO 比 SAC 成功率更高」这一点在 3 个种子下尚未统计分离，只能说"趋势如此"。 但下面这些差异远超噪声，是可靠的结论： 路径效率 0.81 vs 0.39、动作平滑度 0.117 vs 0.517、训练速度 1039 vs 122 步/秒； TD3 的成功率 7% 与 PPO/SAC 完全不在一个量级，也是明确的。

结构层面（算法统一为 PPO）

加深（[64,64,64]）成功率最高（37%），基准 [64,64] 路径效率与平滑度最好（0.81 / 0.117）， 加宽（[256,256]）路径效率最差（0.66）。

⚠️ 但这个差异不显著：三种结构的成功率极差仅 4 个百分点，而种子间标准差平均 达 6 个百分点 —— 在只有 3 个种子的情况下不足以判定哪种结构更优，差异落在噪声范围内。 要下结论需要更多种子（如 10 个）或更长的训练预算。 本实验如实报告这一点，而不是挑一个「最好看」的结构宣称它最优。

已知局限（如实说明）

  • 100k 步下三种算法都没有收敛：uav_ppo_nav 用 40 万步可达 78% 成功率，而本实验中 最高只有 33%。因此本实验比较的是样本效率（同样预算下谁学得快）， 不是各算法的性能上限 —— 要谈上限需要各算法都训到收敛。
  • 未做逐算法调参：为公平起见统一了学习率 3e-4、批大小 256、网络结构与步数预算， 并沿用 SB3 默认超参。off-policy 的 SAC/TD3 对超参更敏感，其表现很可能被默认超参低估。 这是本实验的已知局限，也是后续可改进的方向。
  • 仅 3 个种子：单种子波动可达 ±10 个百分点，报告中所有数值都是 3 种子的均值 ± 标准差。

4. 固定航线巡航

沿闭合航线巡航一整圈，遇到压在航线上的障碍时临时绕行并回到航线；与随机目标导航互补。

本文介绍 src/air/uav_route_cruise 模块：让无人机沿一条固定的闭合航线巡航一整圈， 途中遇到压在航线上的障碍时临时偏离绕行，绕过后自动回到航线。

与 uav_ppo_nav（随机目标点导航）是互补关系：

uav_ppo_nav uav_route_cruise
任务 随机起点 → 随机目标点，到达即结束 给定闭合航线，沿航线巡航一整圈
观测 16 扇形激光 + 目标相对位置 + 速度 24 扇形激光 + 航线几何（横向偏差 / 航向偏差 / 前方 4 m 航点）+ 高度偏差
指标 成功率 / 超时 / 碰撞 完成一圈率 / 平均横向偏差 / 平均完成度
关键能力 点对点规划 循迹 + 遇压线障碍时临时绕避

为什么不能只做「循迹」

如果障碍都摆在航线旁边，那么经典的纯跟踪控制器（pure pursuit，只朝前方航点飞、完全无视障碍） 就能 100% 走完整圈 —— 神经网络没有存在必要。

本模块把一部分障碍直接压在航线上（离航线中心小于障碍半径），于是"贴着中线飞"必然撞上， 想过去就必须偏离航线绕行。这一步把任务从「循迹」变成「循迹 + 局部避障」， 神经网络的价值才体现出来（见「实测结果」一节的对照）。

航线与任务

默认航线是一条 20 m × 14 m 的圆角矩形（角半径 3 m），闭合总长约 62.8 m， 巡航高度 1.5 m，方向为逆时针。用 route.make_route() 或 route_points 参数可以换成其它航线。

graph LR A[航线起点] -->|沿航线循迹| B[巡航段] B -->|遇到压在航线上的障碍| C[临时偏离绕行] C -->|绕过之后| D[回到航线] D --> B B -->|走满整圈 62.8 m| E[完成一圈]

障碍物每个回合随机摆放，其中 on_route_frac 比例的障碍直接放在航线上， 其余放在航线旁侧并保留通行余量。

坐标系约定

全部使用世界系 ENU（东 x、北 y、天 z）。

这是 CarlaAir 环境的现实约束：SimpleFlight 的偏航保持不生效，机头会自行漂移， 用机体系控制会让轨迹随机头打转。改用世界系后，机头怎么转都不影响飞行轨迹。

因此节点发布的速度是世界系速度，桥接必须以 body_frame:=false 启动（见「部署」一节）。

算法流程

训练流程

1. 初始化航线 Route（20×14 m 圆角矩形，L = 62.8 m）
2. 启动 4 个并行 RouteEnv（不同 seed），on_route_frac 从 0.05 开始（课程学习）
3. for 每轮迭代:
   a. 用当前策略 π_θ 在 4 个环境各采样 n_steps 步
   b. 用 GAE 计算优势 Â_t 与回报 R_t
   c. for epoch in 1..10:
        - 打乱样本，按 batch=256 计算 L^CLIP（公式见上）
        - 梯度上升更新 θ、φ
   d. 按训练进度提高 on_route_frac: 0.05 → 0.25（到 60% 进度时升满）
4. 训练结束后导出策略 MLP 权重为 route_ppo_sX.npz
5. 用 numpy 版 MlpPolicy 复算一遍评估（确认导出的权重没坏）

部署流程（ROS 节点）

每 1/20 秒：
1. 从 /uav/odom 取世界系位姿 p 与速度 v
2. 从 /lidar/points 取点云，按高度 ±1.5 m 过滤
3. 算 24 扇区直方图 h（公式见上）
4. 用 route.project(p_xy) 算弧长 s、横向偏差 e、航向偏差 Δψ、前视点相对位置
5. 拼成 30 维观测 o
6. MLP 前向: o → tanh(W0 o + b0) → tanh(W1 x + b1) → W2 x + b2 → clip[-1,1]
7. 映射成世界系速度 (vx, vy, vz)，发布到 /uav/cmd_vel
8. 累计沿航线前进量；走满 L 就把 lap_done 置 true

源代码解析

route.py: Route.project() —— 航线投影

t = np.clip(((p - a) * d).sum(axis=1) / (self.seg_len ** 2), 0.0, 1.0)  # 每段的投影参数
proj = a + d * t[:, None]                                               # 每段上的最近点
dist = np.linalg.norm(p - proj, axis=1)                                 # 到每段的距离
i = int(np.argmin(dist))                                                # 取最近段
s = float(self.cum[i] + t[i] * self.seg_len[i])                         # 弧长进度
cross = d[i, 0] * (p[1] - a[i, 1]) - d[i, 1] * (p[0] - a[i, 0])         # 叉乘 = 带符号横向偏差

向量化到所有段上，一次算出最近段与进度，避免逐段循环。

route_env.py: RouteEnv._sample_obstacles() —— 压线障碍

n_on = int(round(self.num_obstacles * self.on_route_frac))   # 25% 压在航线上
if len(self.obstacles_xy) < n_on:
    if abs(signed) > self.obstacle_radius * 0.6:             # 必须在航线中心附近
        continue
elif abs(signed) < (self.obstacle_clearance + self.obstacle_radius):
    continue                                                 # 其余障碍留出通行余量

这是任务难度的关键开关：on_route_frac=0 时纯跟踪基线也能 100% 完成， 25% 时它掉到 0% —— 任务从"循迹"变成"循迹 + 绕避"。

policy.py: MlpPolicy.forward() —— 纯 numpy 推理

x = np.asarray(obs, dtype=np.float32).reshape(-1)
for w, b in self.hidden:              # 两层 128，tanh 激活（与 sb3 的 net_arch 对应）
    x = np.tanh(w @ x + b)
return np.clip(self.out_w @ x + self.out_b, -1.0, 1.0).astype(np.float32)

部署侧不需要 torch / sb3，只要 numpy：把训练好的 MLP 权重存成 .npz 即可。 激活函数必须与训练时一致（sb3 默认 nn.Tanh），这一点写在 extract_sb3_weights 的注释里。

route_node.py: RouteCruiseNode._build_obs() —— 实机观测

_, s, _, cross = self.route.project(pos[:2])       # 航线几何
tgt = self.route.waypoint_ahead(pos[:2], s, self.lookahead)
d = self.route.seg[_i, :2]                        # 当前段切向
heading = vel[:2] / vn if vn > 1e-3 else tangent   # 速度方向（静止时用切向）
crossang = np.arccos(np.clip(heading @ tangent, -1, 1))  # 航向偏差

与训练环境逐项对齐是关键：训练时喂什么、实机就喂什么。 build_observation 被两边共用，就是为了防止"训练与部署的观测顺序不一致"这种隐蔽 bug。

train.py: CurriculumCallback —— 课程学习

def frac(self, num_timesteps):
    p = min(1.0, num_timesteps / self.total / self.warmup)   # 60% 进度时升满
    return self.start + (self.final - self.start) * p          # 0.05 → 0.25

一开始就给 25% 压线障碍的话，随机探索很难发现"绕过去再回到航线"这种长序列动作， 先给简单的让它学会稳定循迹，再逐步加大避障难度。

训练设计里踩过的坑

  1. 撞机惩罚太轻 → 学会"撞了也无所谓" 初版完成一圈奖励约 600、撞机只扣 30，结果 100% 碰撞。把撞机惩罚提到 -200 后碰撞率降到 0。

  2. 障碍不压线 → 任务失去意义 障碍离航线 ≥2.4 m 时，纯跟踪控制器也能 100% 完成、零碰撞。加 on_route_frac 后基线掉到 0%。

  3. 横向偏差惩罚过强 → 宁可撞也不绕 绕行必然带来横向偏差，w_cross 太大时策略选择硬撞。降到 0.2 后它才愿意绕。

  4. 近距惩罚调大反而更差 试过给「离障碍 < 1.2 m」加连续惩罚（期望比稀疏的撞机信号更好学）， 实测奖励均值被压到负值（-8.6/步），策略变得过度保守、成功率反而下降，因此默认关闭。

5. 城市动态交通下的避障

把静态圆柱换成沿车道行驶的车辆，用规则专家示范 + 行为克隆 + DAgger 学习穿越车流的时机。

﻿# 城市动态交通下的 PPO 避障（uav_traffic_nav）

本页对应当前开发分支。这是一个仍在迭代中的模块，下面区分了"已验证"与"尚未验证"。

要解决的问题

uav_ppo_nav 的障碍是 16 个随机静态圆柱；真实低空场景里最大的风险来自会动的车。 本模块把障碍换成沿车道行驶的车辆，要求无人机从随机起点穿过车流到达随机目标点。

与静态障碍相比，难点在于时机：从车道间穿过时，安全窗口只有 1 秒左右， 只看"当前距离"不够，必须根据车辆速度预判。

方法

观测（34 维）

部分 维度 说明
激光直方图 16 世界系固定方向，0 = 正东，1 = 无障碍
目标相对位置 3 除以 8 m 归一化
世界系速度 3 除以 3 m/s、1.5 m/s
最近 3 辆车 12 每车 4 维：相对位置 (2) + 相对速度 (2)

可以用 --no-traffic-features 训练去掉最后 12 维的消融版本（22 维，只能靠激光直方图感知车辆当前位置）。 本 PR 不保留消融权重，因此最终结果表只比较"带交通特征"的策略与不学习的基线。

动作

4 维：[vx, vy, vz, yaw_rate]，世界系 ENU 速度 + 偏航角速度，归一化到 [-1, 1]。 高度由底层执行器保持（本模块只做水平面避障）。

环境

  • 质点 + 速度环一阶滞后（vel_tau = 0.45 s），与 uav_ppo_nav 一致；
  • 两条车道（y = ±4 m），车辆 2.5–5 m/s，按难度 1–2 辆/车道；
  • 车辆圆形近似（半径 1.0 m），无人机半径 0.3 m（碰撞判定圆半径合计 1.3 m）；
  • 起点/终点采样时保证与车辆至少相距 2.5 m（避免"出生即撞"污染训练信号）。

奖励

进度奖励  +1.0 / 米（朝目标靠近）
碰撞终止  -30
TTC 惩罚  -1.0 × Σ(1 - ttc/2)²   （ttc < 2 s 的每辆车）
平滑/步数 -0.02 / -0.005

TTC（碰撞时间）用二维匀速模型计算；它让"贴着车头抢行"这种高风险的省时行为代价更高。

实验结果（多种子，难度 1.0，100 回合/条件，评测 seed 11）

策略 混合起终点 强制跨路
规则专家（读真值，上界参照） 72% 75%
行为克隆 + DAgger（3 个训练种子） 61.0% ± 3.0% 48.0% ± 3.6%
greedy（无视车辆） 57% 39%
速度障碍法 53% 19%

对照（单种子）：PPO 从零训练 61% / 44%，BC+DAgger+PPO 微调 68% / 41%， 纯行为克隆（无 DAgger）23% / 13%。

"强制跨路"分布：起点固定在路一侧、终点在另一侧，必须横穿两条车道。

示范引导（本模块的关键做法）

PPO 从零训练卡在 44%（强制跨路），因为"等窗口"这类时机决策几乎采不到正样本。 改为两段式：

  1. 规则专家：在车道前 3 m 悬停，检查是否有车会在 1.2 s 内经过穿越走廊； 安全则全速穿过（baselines.expert_action）。强制跨路 75%。
  2. 行为克隆 + DAgger（scripts/bc_train.py）：
  3. 按 6:4 的混合/强制跨路分布采集约 9k 条专家示范；
  4. 3 轮 DAgger：学生自己飞，在每个到达状态贴专家标签再训练；
  5. 3 个种子的学生成功率分别为 20→42→50%、32→30→58%、10→42→60%。
  6. 可选 PPO 微调（train.py --init-from）：同分布 +4，跨路 -11，故不作默认导出。

结论与局限

  • 示范引导有效且稳定：3 个种子 48.0% ± 3.6%（强制跨路）， 高于 PPO 从零（44%）、贪心（39%）、速度障碍法（19%）。
  • 与规则专家（75%）仍差 27 个百分点，瓶颈是"何时开始穿越"的时机精度。
  • 纯 BC 只有 13%：没有 DAgger 的纠偏样本，学生一偏离专家轨迹就崩。
  • 训练环境是质点模型、车辆圆形近似；尚未在 CarlaAir 上做端到端在线飞行。
  • 评测种子会显著影响绝对值（seed 7 时贪心 26%、seed 11 时 39%）， 因此本表固定 seed 11 并同时给出 3 个训练种子的标准差。

附录 A 关键公式

观测归一化（policy.build_observation）：目标相对位置除以 8 m，速度分别除以 3.0 m/s 与 1.5 m/s； 车辆特征的位置除以 12 m、相对速度除以 10 m/s，并裁剪到 [-1, 1]。

动作到速度（policy.action_to_velocity）：

[vx, vy, vz, wz] = a ⊙ [3.0, 3.0, 1.5, 1.0],   a ∈ [-1, 1]^4

碰撞时间（policy.time_to_collision，二维匀速模型）：

r = p_car − p_drone,  v = v_car − v_drone
t* = −(r·v) / |v|²
若 0 < t* ≤ T_h 且最近距离小于 (r_drone + r_car)，记为有碰撞风险

奖励（traffic_env.step）：

r = w_p·(d_{t−1} − d_t) − w_s·||a_t − a_{t−1}||² − w_step
    − w_ttc·Σ_i (1 − ttc_i / T_h)²            # 只对 ttc_i ≤ T_h 的车辆
    + 20·1[到达] − 30·1[碰撞]

默认 w_p = 1.0、w_s = 0.02、w_step = 0.005、w_ttc = 1.0、T_h = 2.0 s。
