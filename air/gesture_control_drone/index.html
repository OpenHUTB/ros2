手势控制 AirSim 无人机

用摄像头 + MediaPipe 识别手部手势，把识别结果转换成指令，通过 ROS 话题交给 控制节点，由控制节点调用 AirSim 多旋翼 API 完成 起飞 / 降落 / 悬停 / 前进 / 上升 / 下降 / 紧急停止，并把载具位姿以 nav_msgs/Odometry（ENU）回传。

源码位于 src/air/gesture_control_drone， 完整运行细节（环境、参数、排查）见模块 README.md。

1. 它解决什么问题

用"抬手"指挥无人机，难点不在识别单个手势，而在让两半程序对同一套词、并且 把 AirSim 的多旋翼接口用对：

摄像头 -> MediaPipe -> 手势 token -> 指令 token -> AirSim 多旋翼 API
        └── 感知节点（发布）──┘└──── 控制节点（订阅 + 执行 + 回传）────┘
                                   │
                                   └─> /drone/odom (Odometry) /drone_state
  • 手势与指令的映射只在一处定义（scripts/gesture_map.py），两个节点 import 同一份常量；AirSim 的每个动作都有实现，缺一个就启动即报错；
  • 线上传输一律用 ASCII token（PALM_OPEN / takeoff …），中文只用于日志与 界面，避免编码与别名问题；
  • 识别结果经过去抖 + 边沿触发 + 冷却才发布：同一个手势一直举着只发一条指令；
  • 控制节点把耗时动作放到工作线程执行，订阅回调只入队；每次 RPC 调用都有 超时保护，仿真器卡住也不会把节点拖死；
  • 有安全限幅：限速、限高、限低；紧急停止默认悬停，不再空中锁桨。

2. 手势与指令

手势 手势 token 指令 token 动作
张开手掌 PALM_OPEN takeoff 解锁 → 起飞 → 爬升到 takeoff_altitude → 悬停（定高仅 *Async 路径生效，同步回退由仿真器默认高度决定，实测约 +1.54 m）
握拳 FIST land 降落
食指指向 POINT forward 机体系向前飞 speed × move_duration
胜利手势 VICTORY up 上升一档（受 max_altitude 限制）
拇指向下 THUMB_DOWN down 下降一档（受 min_altitude 限制）
拇指向上 THUMB_UP hover 原地悬停（稳定）
OK 手势 OK estop 紧急停止（默认悬停，可配 land/disarm）

另外还有两个不占用手指的指令，可直接用话题触发（便于联调/答辩演示）： yaw_left / yaw_right（按 yaw_rate 偏航）与 home（返航到原点上方）。

3. 环境要求

位置 项目 版本
宿主 操作系统 Windows 10/11
宿主 模拟器 AirSim（Blocks，UE 4.27，RPC 41451）
客户机 操作系统 Ubuntu 20.04.6
客户机 ROS Noetic（ROS 1）
客户机 Python 3.8
客户机 依赖 python3-opencv python3-numpy python3-pil（apt）
mediapipe(0.10.x) airsim（pip，见 requirements.txt）

摄像头必须接在跑 ROS 的那台机器上；虚拟机里需要先把 USB 摄像头透传进来。 用的是经典版 AirSim 时客户端是 airsim（不是 cosysairsim）。

4. 运行

# 1) 编译
cd ~/uav_ws && catkin_make && source devel/setup.bash

# 2) 宿主机启动 AirSim 仿真器，并放行 41451 端口

# 3) 启动本模块（跨机部署时用 airsim_ip 指定宿主 IP）
roslaunch gesture_control_drone main.launch airsim_ip:=192.168.80.1

# 4) 只看识别效果、不动飞机
roslaunch gesture_control_drone main.launch start_drone_control:=false show_window:=true

# 5) 没有 ROS 也能验证手势与词表（单机演示，画一台"虚拟无人机"）
rosrun gesture_control_drone gesture_demo.py

预期日志（起手"张开手掌"）：

5. 话题接口

方向 话题 类型 说明
发布 /gesture_command std_msgs/String 指令 token，边沿触发
发布 /gesture_state std_msgs/String 当前识别到的手势 token（变化时才发）
订阅 /gesture_command std_msgs/String 控制节点订阅；词表外的字符串会被忽略并告警
发布 /drone/odom nav_msgs/Odometry 载具位姿与速度（ENU，frame_id=world），可加进 RViz
发布 /drone_state std_msgs/String 执行结果，如 takeoff OK / down FAIL 已到最低高度…

排查"为什么没触发"：

rostopic echo /gesture_state     # 识别有没有出结果
rostopic echo /gesture_command   # 指令有没有发出来
rostopic echo /drone_state       # 执行成功/失败原因
rostopic echo /drone/odom        # 位姿（确认飞机真的动了）
rostopic pub -1 /gesture_command std_msgs/String "data: 'takeoff'"   # 绕过识别直接测执行

为什么直连 AirSim、而不是走 carlair_ros_bridge + /uav/cmd_vel？ 本轮验证用的是经典版 AirSim（Blocks, UE 4.27），这套环境里没有 carlair_ros_bridge（它服务于 CarlaAir / Cosys-AirSim 那套栈）。直连时桥接层原本 提供的安全逻辑由本模块自己补齐：指令冷却、单次 RPC 超时（command_timeout， 超时判失败而非永久阻塞）、限速/限高/限低、退出时先悬停再交还控制权、 紧急停止三选一。若之后接入 CarlaAir 栈，只需把 drone_client.py 换成发布 /uav/cmd_vel——它是唯一与仿真器耦合的模块，感知/词表/闸门那一层不用动。

6. 参数

参数在 config/gesture_control.yaml，由 launch 载入各节点的私有命名空间。

参数 默认 说明
camera_index 0 摄像头索引，打不开时自动尝试 0~4
show_window false 是否弹出识别预览窗
publish_rate 10.0 识别循环频率 (Hz)
stable_frames 3 连续多少帧识别到同一手势才算数（去抖）
command_cooldown 1.5 同一条指令的最小间隔 (s)
command_topic /gesture_command 指令话题（两端共用）
airsim/ip 127.0.0.1 仿真器地址；跨机填宿主 IP
airsim/port 41451 RPC 端口
airsim/vehicle_name 空 留空 = 默认载具（Drone1）
estop_action hover 紧急停止：hover / land / disarm（空中锁桨会坠落）
takeoff_altitude 3.0 起飞后爬升高度 (m)，不得超过 max_altitude
speed 1.0 前进/上升/下降速度 (m/s)
max_speed 3.0 速度上限 (m/s)
max_altitude 30.0 高度上限 (m)
min_altitude 0.5 高度下限 (m)，到这里拒绝下降
move_duration 1.0 单次位移/偏航持续时间 (s)
yaw_rate 30.0 偏航角速度 (deg/s)
command_timeout 10.0 单次 RPC 超时 (s)，超时视为失败
takeoff_timeout 60.0 起飞（含 moveToZAsync 定高）超时 (s)；慢仿真器可调大
land_timeout 60.0 降落超时 (s)；3 m 降落实测约 14~20 s，不能用 command_timeout
state_lock_timeout 0.1 读状态抢不到 RPC 锁时的等待上限 (s)；降落时锁会被占 20 s，取值必须很短，否则 /drone/odom 会停更
state_rate 5.0 /drone/odom 发布频率 (Hz)，0 = 关闭
connect_retries 3 连接 AirSim 的重试次数

8. 常见问题

现象 原因与处理
无法打开摄像头（已尝试索引 [0,1,2,3,4]…） 摄像头没接在 ROS 机器上 / 没透传进虚拟机 / 被占用。ls /dev/video* 确认；可用 GESTURE_CAMERA_BACKEND=CAP_V4L2
连接 AirSim x.x.x.x:41451 失败 仿真器没启动、airsim_ip 填错、或 41451 被防火墙拦（Windows 需加入站规则）
缺少 airsim 客户端：pip3 install airsim 只装了 apt 依赖。经典 AirSim 用 airsim，Cosys-AirSim 才用 cosysairsim
手势识别到了但飞机不动 看 /gesture_command；没有 → 去抖参数或手势不在词表；有 → 看 /drone_state 与 [drone] 日志
一直举着手，指令只发一次 设计如此（边沿触发）。手放下再举起才再次触发
已到最大高度 / 已到最低高度 触发了 max_altitude / min_altitude 保护；改参数或改用降落
起飞后高度不对 检查 takeoff_altitude；AirSim 的 takeoffAsync 只到默认高度，本模块会再 moveToZAsync 定高
中文显示成方块 缺中文字体；Ubuntu 装 fonts-wqy-zenhei，Windows 自带 simhei
手指旋转超过 90° 后识别率下降 手指伸展判定基于"指尖在 PIP 关节上方"的启发式，掌心朝镜头、手指大致朝上时最稳

9.2 虚拟机内 ROS → AirSim 真机飞行（实测）

在 Ubuntu 20.04 + ROS Noetic 虚拟机里跑节点，AirSim Blocks 跑在 Windows 宿主上 （airsim_ip:=192.168.80.1），通过 rostopic 下发指令验证了完整控制链路：

节点：/drone_control_node   /gesture_ros_node   /rosout
话题：/drone/odom  /drone_state  /gesture_command  /gesture_state

9.3 实跑才暴露的两个坑（已修）

  1. catkin_install_python 不能用来装"辅助模块" 它在 devel 空间给每个脚本生成的是启动器（exec(compile(...))）， 被启动的文件能跑，但 from drone_client import AirSimDrone 会 ImportError —— 因为拿到的是启动器而不是真模块。 → 现在只把 4 个入口（main / gesture_ros_node / drone_control_node / gesture_demo）交给 catkin_install_python，辅助模块改用 install(FILES)； 节点里再加一段 sys.path 引导，保证从源码目录也能 import。
  2. VMware 透传的摄像头默认格式读不到帧 /dev/video0 能 open，但 cap.read() 一直 select() timeout （默认 YUYV 720p 带宽不够）。→ camera_utils.open_capture() 现在默认设 MJPG（可用 GESTURE_CAMERA_FOURCC 覆盖）并降到 640×480， 同一台机器上立刻出画面（shape=(480, 640, 3)）。

同步回退模式的结果语义（如实说明）：客户端没有 *Async 时，同步 takeoff / land 是"发完即弃"，节点只能确认命令已下发，拿不到 AirSim 的执行结果。 例如飞机已在空中再发 takeoff，AirSim 会返回 Cannot perform takeoff because vehicle is already moving，但节点侧仍按"已下发"记录。 有 *Async 时 join() 会把异常抛出来。

两个额外结论：

  • 定高只在 *Async 路径生效：这里 takeoff 到 2.63 m（takeoff_altitude=3.0）， 而同步回退只到仿真器默认高度（约 +1.54 m）。

10. 客户端兼容层与已知坑

10.1 先澄清一个容易误判的点

takeoffAsync / landAsync / hoverAsync / moveToZAsync / goHomeAsync 都是 Python 客户端的方法，内部只是 call_async('takeoff', ...) 之类的包装：

# microsoft/AirSim  PythonClient/airsim/client.py
def takeoffAsync(self, timeout_sec=20, vehicle_name=''):
    return self.client.call_async('takeoff', timeout_sec, vehicle_name)
def goHomeAsync(self, timeout_sec=3e+38, vehicle_name=''):
    return self.client.call_async('goHome', timeout_sec, vehicle_name)

也就是说 服务端从来只有 takeoff / land / hover / goHome（所有 AirSim 版本都一样）， "异步"是客户端把请求发出去后不等结果。所以"服务端没有 takeoffAsync"不是老 build 的特征。

本模块的 api_mode 只解决另一个问题：某些客户端（例如自写的精简客户端、很老的 Python 客户端）不提供 *Async 方法，那时回退到同名同步方法：

客户端方法 服务端方法 缺 *Async 时的回退
takeoffAsync(timeout) takeoff takeoff(timeout, vehicle_name)，阻塞
landAsync(timeout) land land(timeout, vehicle_name)，阻塞
hoverAsync() hover hover(vehicle_name)
moveToZAsync(z, v) moveToZ moveToZ(z, velocity, timeout, yaw_mode, lookahead, adaptive, vehicle_name) —— 7 个参数
goHomeAsync(timeout) goHome goHome(timeout, vehicle_name)，阻塞

10.2 五个已知坑（都已处理）

  1. 同步 takeoff / land 会阻塞到动作完成 3 m 高度按 ~0.22 m/s 下降约需 14 s，放在调用线程里会把 ROS 回调/定时器堵住。 → 用独立连接发命令、后台线程等待、调用方立即返回；状态靠轮询 /drone/odom。
  2. 降落比 command_timeout(10 s) 慢 从 3 m 降落约 14 s，套用 10 s 会误判超时。 → takeoff 与 land 各有独立上限 takeoff_timeout / land_timeout（默认 60 s）。
  3. msgpack-rpc 客户端不是线程安全的 控制节点的状态定时器（5 Hz 读状态）与指令工作线程共用同一个连接， msgpackrpc 的 Session 没有发送锁 —— 这是"响应错位/超时"的真正根因。 → 所有对主客户端的 RPC 由 _api_lock（threading.RLock）串行化。
  4. landed_state 的取值 官方 airsim.types.LandedState 是 Landed = 0、Flying = 1 （旧代码把 0/1 映射写反了，已修正）；起降判定仍以高度为准，不依赖它。

  5. goHomeAsync 第一个位置参数是超时，不是速度 （旧代码误传 speed，等于给返航设了 1 s 超时，已改为 60 s）。

  6. 同步回退必须按服务端签名传参 —— 例如 moveByVelocityBodyFrame 要 (vx, vy, vz, duration, drivetrain, yaw_mode, vehicle_name) 共 7 个， rotateByYawRate 要 (yaw_rate, duration, vehicle_name) 3 个； 少传会报 Function ... was called with an invalid number of arguments。 drone_client 现在按完整签名调用，vehicle_name 用关键字传（对没有该形参的 旧客户端自动回退）。 实机验证：forward / up / down / yaw_left 都能让飞机真实移动。

  7. hover() 在移动中调用会让飞机掉高度（在等价 msgpack-rpc 客户端上观察到，未在官方客户端上复现）—— 实测：forward 之后调用 hover，飞机从 0.85 m 一路降到地面（-0.68 m）；而静止时调用 hover 是安全的（6 s 高度不变）。 现在移动 / 偏航 / 急停之后一律改用零速度刹车 （moveByVelocityBodyFrame(0, 0, 0, 0.5)）：实测 forward 位移约 0.9 m 后停住， 高度稳定在 0.78~0.85 m；停住后仍有 ±0.2 m 的位置保持抖动（在当前环境下观察到的位置保持抖动）。
